# MongoDB integration

MongoDB stores flexible transportation content in `vehicle_documents`, `passenger_feedback`, `announcements`, and `trip_media`. Collections have no strict document validators; optional values and metadata can differ between records. Vehicle documents support images, registration, insurance, and inspection files with expiry and URL metadata. Feedback can represent reviews or complaints linked to route, trip, vehicle, and driver IDs. Announcements include audience, priority, status, date range, and optional route/trip targeting. Trip media supports photos, videos, journey documents, captions, URLs, and uploader identity.

The backend checks `MONGODB_URI` and `MONGODB_DATABASE`, then pings MongoDB before reporting `connected: true`. The health endpoints are `/api/health/mongodb` and `/api/health/databases`. Passenger review writes use `POST /api/mongodb/feedback` and persist to `passenger_feedback`; the Admin page reads that collection through `GET /api/mongodb/feedback`. Feedback reads and writes never use an in-memory fallback, including in `DATABASE_MODE=demo`; MongoDB connection and insertion failures return an error and cannot report a successful save. Admin-created announcements are written to `announcements`; the API accepts audiences `all`, `passengers`, and `drivers`. Older `passenger_reviews` and `travel_announcements` records remain readable by the broader content feed during migration, while new feedback and announcement writes use the current collection names. Other MongoDB Content sections may use the existing labeled in-memory demo fallback.
